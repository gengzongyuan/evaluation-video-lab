# LF-02《Trace 是什么》口播稿（Xiaoxiao Neural）

用途：给 `zh-CN-XiaoxiaoNeural` 配音使用。建议 `rate=-5%`，语速约 230–260 字/分钟，句间停顿 250–400ms。禁止整段拉伸到固定 180 秒；口播多长，成片就多长。箭头和英文术语处稍停。

承接 LF-01：上一集建立 Langfuse 概念，本集只讲清 Trace 和普通日志差在哪里。

## 口播分镜（20 段，约 6–10 秒一段）

| 段 | 口播 |
|---:|---|
| 01 | 用户只发了一句话。后台可能已经跑完检索、工具和模型。只看最终答案，你看不出哪一步出错。 |
| 02 | 普通日志常常只留下一句请求失败，或者一句最终回复。中间过程是黑的。 |
| 03 | Langfuse 把这一整次请求记成一条 Trace，追踪。你可以把它理解成一次完整的就诊记录。 |
| 04 | Trace 是容器，不是某一个模型答案。它把这次请求从头到尾串起来。 |
| 05 | 和普通日志的差别在这里：日志是一串散落的行，Trace 是一棵能展开的调用树。 |
| 06 | 树里每一个可观察动作，叫 Observation，观察节点。父节点下面还能挂子节点。 |
| 07 | 普通处理步骤，比如检索或工具调用，通常记成 Span，步骤。 |
| 08 | 模型真正生成文字的那一步，记成 Generation，生成。它会带上输入、输出和模型信息。 |
| 09 | 所以你能从总耗时往下钻：是检索慢，还是模型慢，还是工具报错。 |
| 10 | 先看一条最小链路：用户提问，系统检索，再调用工具，最后模型生成答案。 |
| 11 | 这整次请求共用一条 Trace ID。排错时先拿这个 ID，不要只翻终端滚动日志。 |
| 12 | 失败时先问三句：失败节点是哪一个？它的输入是什么？耗时和输出有没有异常？ |
| 13 | 打开这条 Trace，你要核对输入、输出、时间和状态，而不是只看页面有没有数据。 |
| 14 | 但要注意，页面能打开，不代表刚才那条 Trace 已经写入成功。 |
| 15 | 例如 health 返回 200，只能说明健康检查在那个时间点通过。 |
| 16 | 它不能证明新 Trace 已经写进去，更不能证明你能用同一个 ID 回读到同一条记录。 |
| 17 | 真正验收时，要发出请求，拿到 Trace ID，再读取同一条记录核对。 |
| 18 | 还有一层边界：单条 Trace 只能说明这一次发生了什么，不能代表整体稳不稳定。 |
| 19 | 本集只讲清 Trace 和普通日志的差别。画面是 prototype / L1 示意，不代表当前实例已经写入或回读成功。 |
| 20 | 下一集我们拆开 Span 和 Generation：为什么模型调用要单独记？ |

## TTS 标注建议

- 声线固定 `zh-CN-XiaoxiaoNeural`，`rate=-5%`；不要用 macOS `say`，也不要把原速音频拉伸到固定 180 秒。
- “Langfuse”读作“Lang-fuse”，不要逐字母拼读。
- 第一次出现时中英并读：Trace，追踪；Observation，观察节点；Span，步骤；Generation，生成。之后统一保留英文词。
- “不是……而是……”少用；第 04、05 段各只保留一个对比点，不要堆叠否定句。
- 每 2–3 段插入约 300ms 停顿；段尾不要自动升调。
- 字幕按句子切，不要把整段口播一次性铺满屏幕。

## 事实边界

所有“prototype / L1”“health 200 ≠ new Trace”表述必须保留。本稿只解释概念和验收口径，不得把示意图、历史截图或健康检查包装成当前 Langfuse 实例已完成 Trace 写入、Worker 消费或 UI/API 回读。单条 Trace 不能口播成整体稳定性或模型更好。公开稿件不得出现内网地址、项目密钥、Authorization 头或真实用户内容。
